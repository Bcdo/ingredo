# Recipe Management — Design Spec

**Date:** 2026-07-05
**Slice:** First feature slice of the Phase 1 local MVP (frontend only, no backend).
**Scope:** Recipe CRUD — list, create, view, edit, delete — with ingredients and instructions. Recipe scaling and unit conversion are the next slice.

## Goals

- A user can create, browse, view, edit, and delete recipes, entirely offline, stored in SQLite on the device.
- Establish the app skeleton (tabs, design tokens, i18n, data layer, test infrastructure) that later slices build on.

## Non-goals (deferred)

| Deferred item | Comes with |
|---|---|
| Recipe scaling, unit conversion | Next slice |
| Photos, URL import, natural-language ingredient entry | Later slice |
| Filter chips (Quick, Vegetarian…), favourites, long-press quick sheet | Later slices (need fields/features that don't exist yet) |
| Ingredient `category` | Shopping slice |
| `household_id`, `version`, sync fields | Phases 4–5 |
| Drag-reorder of ingredients/instructions | Later slice |
| Settings screen / language switcher | Later slice (device locale decides for now) |

All omissions are additive migrations or additive UI later; nothing in this slice blocks them.

## Key decisions

1. **Data layer: Drizzle ORM over expo-sqlite.** Typed schema, `drizzle-kit`-generated SQL migrations, reactive reads via `useLiveQuery`. Works in Expo Go. Chosen over plain expo-sqlite (more manual work each slice) and WatermelonDB (requires a dev client; Expo Go stops working).
2. **Tabs follow `design/DESIGN.md`:** Today · Plan · Recipes · Shop. Today/Plan/Shop are placeholders. This supersedes the older Recipes/Week/Shop/Settings recommendation in `DESIGN_SYSTEM.md`/`UX_NOTES.md`.
3. **Structured ingredient entry, not natural-language parsing.** The app must support Norwegian and English (more languages possible later); NL parsing is language-dependent (ss/ts/stk vs tbsp/tsp/pcs, decimal commas). Structured entry sidesteps this: numeric quantity + unit picker storing canonical codes with localized labels. This supersedes `DESIGN.md` §3.7's natural-language entry for now.
4. **i18n from the start:** `i18n-js` + `expo-localization`, `en` + `nb` translation files, every UI string through `t()`. Retrofitting i18n after many screens exist is painful; scaffolding now is cheap.
5. **UUIDs client-side from day one** (via `expo-crypto`) so future sync needs no ID remapping.
6. **Soft delete** (`deleted_at`), matching `ARCHITECTURE.md` and the future sync model ("soft-deleted records stay deleted").

## Data model

Three tables (Drizzle schema in `lib/db/schema.ts`):

### `recipes`
| Column | Type | Notes |
|---|---|---|
| `id` | text PK | UUID, client-generated |
| `title` | text | required |
| `description` | text | nullable |
| `servings` | integer | required, default 4, min 1 |
| `notes` | text | nullable |
| `created_at` | integer | epoch ms |
| `updated_at` | integer | epoch ms |
| `deleted_at` | integer | nullable; soft delete |

### `recipe_ingredients`
| Column | Type | Notes |
|---|---|---|
| `id` | text PK | UUID |
| `recipe_id` | text FK → recipes | cascade delete |
| `name` | text | required |
| `quantity` | real | nullable ("salt to taste") |
| `unit` | text | nullable; canonical code (`g`, `kg`, `ml`, `dl`, `l`, `ts`, `ss`, `stk`, …) or free text fallback |
| `sort_order` | integer | entry order |

### `recipe_instructions`
| Column | Type | Notes |
|---|---|---|
| `id` | text PK | UUID |
| `recipe_id` | text FK → recipes | cascade delete |
| `text` | text | required |
| `sort_order` | integer | entry order |

## Data access layer

`lib/db/`:
- `schema.ts` — Drizzle table definitions.
- `client.ts` — expo-sqlite database + Drizzle client singleton.
- `recipes.ts` — repository: `createRecipe`, `updateRecipe`, `softDeleteRecipe`. Each writes recipe + ingredients + instructions in a single transaction (update = replace child rows). `updated_at` maintained on every write.
- Migrations generated by `drizzle-kit`, bundled with the app, applied on startup via `useMigrations`; minimal loading state while running, retry screen on failure.

Reads go through `useLiveQuery` (list, detail) so screens update reactively. Screens never touch SQL directly.

## Navigation & screens

Expo Router. Tab skeleton in `app/(tabs)/`: `today.tsx`, `plan.tsx`, `recipes.tsx`, `shop.tsx`. Placeholders are calm screens (icon + one-line "coming soon" copy), never dead ends.

### Recipes tab — list (`app/(tabs)/recipes.tsx`)
- Two-column card grid (per `DESIGN.md` §3.3), text-forward since there are no photos: title (Fraunces), servings line.
- Persistent search field filtering client-side on title **and ingredient names**.
- Clay **+** FAB → create.
- Empty state (§3.8): friendly copy + one obvious action (create your first recipe).

### Recipe detail (`app/recipe/[id]/index.tsx`, pushed over tabs)
- One scroll: title/description → servings → ingredients (quantities in clay) → numbered method steps (large numerals, ~1.6 line-height) → notes.
- Header actions: Edit; Delete behind a confirmation dialog → soft delete → back to list.
- Missing/deleted id → redirect to list.

### Recipe form (`app/recipe/new.tsx`, `app/recipe/[id]/edit.tsx`)
- Both are full-screen modal sheets rendering a shared `RecipeForm` component.
- Cancel left, Save right, always visible. **A recipe with only a title is valid.**
- Fields: title (required), description, servings (stepper, min 1), notes.
- Ingredients: rows of quantity (numeric, accepts `,` and `.` decimals) + unit (pill picker over canonical list, localized labels, "other…" free-text fallback) + name. Add via button, remove via row icon. Order = entry order.
- Instructions: numbered multiline text boxes, add/remove, entry order.

## Components & design language

`components/ui/` primitives, styled with NativeWind using `design/DESIGN.md` tokens:
- Tailwind theme extension: cream `#FBF7F1`, linen `#F3ECE1`, clay `#C96B45`, sage `#7D9474`/`#50664A`, butter `#F3E2BE`, ink `#3A322B`; 18–22 px card radii.
- Fonts: Fraunces (display) + Karla (body) via `expo-font`.
- Primitives: `Button` (clay primary / linen ghost, ≥56 pt), `Card`, `Input`, `Stepper`, `EmptyState`.
- Tone: warm, calm; no red error banners; large touch targets.

The stock template components (`EditScreenInfo`, `ScreenContent`, etc.) are removed as part of this slice.

## i18n

- `i18n-js` + `expo-localization`; device locale, English fallback.
- `lib/i18n/` with `en.json`, `nb.json`; all UI strings via `t()`.
- Unit labels keyed by canonical unit code in the same translation files.
- No language switcher UI yet.

## Validation & error handling

- Title: Save disabled until non-empty (quiet hint, not an error state).
- Servings: stepper enforces positive integer by construction.
- Quantity: unparseable input → ingredient saves name-only; never blocks saving.
- Ingredient rows with no name are dropped on save.
- Unsaved-changes guard on Cancel with edits.
- Failed DB write → calm butter-toned inline notice ("Couldn't save — try again").
- Migration failure at startup → retry screen.

## Testing

- First test infrastructure in the repo: `jest-expo` + React Native Testing Library, wired as `npm test`.
- **Repository tests** run the real Drizzle schema + queries against `better-sqlite3` in Node: create/read/update/soft-delete; transaction atomicity (child-row failure rolls back the recipe); soft-deleted recipes excluded from lists.
- **Utility tests:** quantity parsing (`1,5` → `1.5`), search filtering, form-state ↔ row mapping.
- Screens: manual testing per `TESTING.md` checklist (Android, empty states, long text, small screens).
- Final verification: run in Expo Go, walk create → list → view → edit → delete.
